# ADR-049: Telegram Media Metadata-only Shadow v1

Status: R1 repository-only / inactive / not installed

## Decision

Telegram image events receive a dedicated pre-download observation path. The
active text conversation path remains unchanged. The path has two processes:

1. `telegram_media_metadata_shadow_gateway.py` verifies the signed channel
   event, replay claim, time window, and existing verified Owner binding;
2. the independent `telegram_media_metadata_shadow` worker receives only an
   identity-free metadata datagram and appends a bounded trace.

Neither process imports a Telegram SDK, downloads an attachment, opens an image,
calls the Pillow decoder, invokes a model, reads or writes memory, calls a tool,
or changes the visible reply. Unsupported events remain on the existing silent
non-text boundary.

## Retained metadata

Only these media-shape facts may cross into the trace worker:

- a fresh random observation UUID;
- `image_component` as a fixed attachment-kind enum;
- attachment count bucket `1` or `2-4`;
- whether AstrBot supplied any `Plain` component alongside the image;
- delivery latency bucket;
- rounded observation timestamp generated by the worker;
- fixed boundary, Shadow, visible-path, and production-effect enums.

The worker rejects any extra field. In particular it never receives Telegram
User ID, binding/principal/namespace, message ID, update ID, caption text, image
reference, file ID, URL, local path, bytes, MIME, dimensions, hashes, secrets,
tokens, model output, prompt data, or memory data.

## Authentication boundary

AstrBot inspects component classes only. It does not access `Image.file`,
`Image.url`, `Image.path`, convert an image, or call Telegram. It signs a small
shape envelope using the existing channel-signing secret. A separate gateway
worker verifies the signature, time window, durable replay claim, and existing
verified Owner binding before producing the identity-free datagram.

The raw account identifier exists only transiently inside the signed
AstrBot-to-authentication envelope and is never logged or forwarded to the
metadata worker. Authentication failures emit only fixed stage codes.

## Isolation and failure behavior

The authentication socket and metadata socket have independent markers,
services, users, runtime directories, and permissions. Either process may fail
or be absent without changing the text conversation path or producing a visible
Telegram reply. Enqueue is one-shot, non-blocking, and has no retry.

No automatic login, download, decode, provider call, or repair is part of this
stage. The already installed decoder remains disabled and its approval marker
remains absent.

## Activation gates

R2 binds the authentication process and trace worker to two independent,
deterministic content-addressed releases. Rendered systemd units may reference
only those exact release roots plus one exact Core release for the identity
fingerprint implementation. No `current`, `latest`, mutable repository, or
`/usr/local` code path is accepted.

The two Unix socket parent directories are created by a dedicated tmpfiles
contract before either socket starts. The authentication directory is owned by
the dedicated Telegram Gateway identity and is not made world-traversable. The
metadata Worker directory is traversable but contains only a group-writable
identity-free datagram socket. Socket file modes remain authoritative.

R1 only places source, tests, templates, and this ADR in the Deploy repository.
Later steps require separate content-addressed build, disabled/inactive install,
a synthetic no-content probe, and explicit persistent Shadow activation. A real
Telegram image acceptance test is not requested until those gates pass.
